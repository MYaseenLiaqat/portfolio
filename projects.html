APPLIED AI / RESEARCHAI Learning ResearchControlled assistance, frozen provenance, deterministic grading, and research integrity.Open case study +

What I was solving. I built an experimental learning platform where AI can support a learner without silently becoming the learner, while keeping study conditions reproducible.

I freeze provenance. I persist the learner condition, prompt version, model/provider identifiers, module version, and AI cap instead of inheriting them from mutable runtime settings.

I control assistance. AI access is condition-aware, attempts are ownership-checked, supported sessions expire, and the interaction count is capped.

I grade deterministically. Code runs in a fresh namespace with an explicit result variable, while automated tests cover access, submission, scheduling, seed data, and prompt integrity.

FULL-STACK AIReflctA product-first AI architecture connecting application state, retrieval, and inference.Open case study +

What I was solving. I wanted Reflct to feel like one coherent productivity product rather than a dashboard with an AI chat box attached. Journals, habits, and goals are persistent product data, and the AI companion should use relevant parts of that context when responding.

I keep product state central. Next.js drives the product interface, while Supabase stores the persistent user and application data that the experience is built around.

I put retrieval before inference. LlamaIndex selects relevant context from the stored product data before the request reaches the model, so the response can reflect the user's own activity instead of relying on a generic prompt alone.

I keep inference as one service inside the product. Groq handles the LLM call, while the application controls the user state and retrieval flow around it. The generated response then returns to the same Next.js experience.

The important design choice is that the product owns the user state. Retrieval assembles the relevant context; inference uses that context and returns the response to the same product flow.

PRODUCTION BACKENDMabros CouriersAppropriately scoped backend engineering for a real local courier operation.Open case study +

What I was solving. I needed a dependable backend where orders, deliveries, tracking, and service integration could move through one API surface for a real local courier operation.

I centralize the workflows. The Flask API is the application boundary for the core operational actions.

I keep the infrastructure practical. Firebase supports the data needs without adding complexity beyond the client's scale.

I standardize delivery. Docker packages the service so development and production share the same boundary.
